# Состояние работ: зарядка и быстрая зарядка на nabu (Windows)

Дата: 2026-09-17. Составлено по итогам работы с планшетом по SSH.

## 1. Коротко

- Программная часть (драйвер, комплект, профили, телеметрия, журнал, защита, документация,
  воспроизводимая подписанная сборка) — готова и проверена.
- Драйвер устанавливается, загружается, устройство создаётся, шина открывается,
  ресурс подключения разбирается, запросы к узлу уходят.
- **Зарядка под Windows не работает.** Зарядный насос LN8000 не опознан: системный объект
  подключения (`\Device\RESOURCE_HUB\<id>`) отвергает запрос последовательности I²C
  кодом `STATUS_INVALID_PARAMETER` (0xC000000D) при любом оформлении запроса.

## 2. Что установлено точно (с доказательствами)

| Факт | Доказательство |
|---|---|
| Чип на I²C 0x51, шина QUPv3 SE4 = ACPI `I2C5` | дерево устройств `ln8000_charger@51` в `qupv3_se4_i2c`; карта ACPI: `QCOM057E`/`PEIC` на `I2C5` |
| У узла ровно одно подключение: класс SERIAL (2), тип I2C (1), id 1 | перечень ресурсов `_CRS` в реестре узла (`ConnCount`, `C0Class`, `C0Type`, `C0Low`) |
| Путь к узлу строится верно | тот же путь использует штатный драйвер (`FUN_14000acd0` в `qcpmicEIC8150.sys`) и драйверы `qcpmictcc8150`/`qcusbcucsi8150` |
| Узел принимает управление соединением | `IOCTL_SPB_LOCK_CONNECTION` → статус 0 |
| Узел отвергает последовательности | `IOCTL_SPB_EXECUTE_SEQUENCE` → 0xC000000D на 10+ вариантах оформления |
| Цель родителя принимает все запросы SPB | семь кодов запросов → статус 0, но чтение регистров даёт нули (адрес не передаётся) |
| Штатный драйвер узла на этой системе тоже не проходит | его запрос подключения `0x32C004` к родителю → `0xC0000003`/`0xC0000034`; к узлу → 0xC0000010 |
| Откат работает | снятие нашего драйвера возвращает узел драйверу `qcpmicEIC`, устройство OK, код 0; повторная установка проходит |
| Зарядка не идёт | 55 % → 55 % за 150 с при статусе «на питании» |

## 3. Что проверено и исключено по оформлению запроса

Размер списка передач (48/80/112 байт), семантика поля `Size` (заголовок против полной длины),
размещение данных (в области передач / в буфере данных / в переданном выходном буфере),
формат буфера (`Simple`, `SimpleNonPaged`), завершающий элемент с направлением `None`,
наличие и отсутствие выходного буфера, маска доступа при открытии узла
(`GENERIC_READ|GENERIC_WRITE` и как у штатного драйвера `0x1F01FF`), удержание соединения,
синхронная и асинхронная отправка. Итог один — `0xC000000D`.

## 4. Где остаётся неизвестное

Проверка внутри системного объекта подключения. Он создаётся системной библиотекой SPB
(`spbcx.sys`; в ней есть строка `RESOURCE_HUB` и объект `SPBCLIENT`). Трассировочных строк для
проверки списка передач в библиотеке нет, поэтому её нужно искать структурно — по обращениям
к полям заголовка списка, а не поиском константы.

## 4a. Новое: узел проверен из пользовательского режима (быстрый канал)

Узел `\Device\RESOURCE_HUB\0000000000000001` **открывается из пользовательского режима** и
принимает запросы. Это даёт канал проверки за секунды, без перезагрузок. Полученная матрица:

| Запрос шины | Без буферов | Со списком передач |
|---|---|---|
| Захват контроллера | не поддерживается (0x32) | не поддерживается |
| Освобождение контроллера | не поддерживается (0x32) | не поддерживается |
| Последовательность | **требует буфер (0x7A)** | неверный параметр (0x57) |
| Захват соединения | 0x16 | 0x16 |
| Освобождение соединения | **поддерживается** | 0x16 |
| Полный дуплекс | нет функции (0x01) | нет функции |
| Особый | нет функции (0x01) | нет функции |

Что это доказывает:

1. Узел **разбирает** запрос последовательности — без буфера он прямо просит буфер (0x7A),
   то есть обработчик существует и маршрут верный.
2. При наличии буфера он отвергает содержимое (0x57) — и делает это **при любом содержимом**:
   с нулевым размером заголовка, с нулевым числом передач, с разными направлениями и форматами,
   с длиной входа 48/56/64/80, до и после защёлки соединения. Значит это не наша ошибка
   оформления: рамка совпадает с тем, что пишет штатный драйвер.
3. Узел реализует только уровень **соединения** (защёлка/освобождение), уровня контроллера
   у него нет (0x32) — это узел ресурсов, а не полноценный посредник шины.

## 4b. Новое: где узел в дереве устройств

Родитель нашего узла — **шина ACPI** (`ACPI_HAL\PNP0C08\0`), а не контроллер I²C. Это
штатная схема для устройств, описанных в ACPI с ресурсом подключения: клиент обязан идти
через узел ресурсов. То есть выбранный маршрут верный, а упор — в самом узле.

## 4c. Новое: расшифрован `_CRS` узла и проверены все подключения

В живом дампе DSDT (`09-acpi-nabu/live-dump/acpi-dump/DSDT_explicit.dsl`, 3.2 МБ, 78 758 строк)
устройство `PEIC` разобрано до байтов. Его `_CRS` — дескриптор подключения (тип `0x8E`,
длина 25), внутри прямо записаны:

- адрес устройства **`0x51`** — это адрес LN8000;
- имя контроллера **`\_SB.I2C5`** — той самой шины, что в системе работает как
  `ACPI\QCOM0511\5` (состояние OK, служба `qci2c`).

Строки `LN8000` / `LIONSEMI` в дампе отсутствуют полностью — узел описан обобщённо,
поэтому его и не узнают по имени.

Состояние шін в системе (один запрос вместо сотни):

| Шина | Устройства | Состояние | Служба |
|---|---|---|---|
| I²C (QUPv3) | `ACPI\QCOM0511\1`, `\5`, `\8` | OK, код 0 | `qci2c` |
| SPMI | `ACPI\QCOM050C\1` | OK, код 0 | `qcspmi` |
| SPI | `ACPI\QCOM050F\4`, `\13` | OK, код 0 | `qcspi` |

То есть **шина I²C жива**, а узел в состоянии ошибки — единственный на планшете (из 108
устройств `ACPI\QCOM*` без проблем 107).

### Перебор идентификаторов подключений

Обрабец Microsoft (`SpbTestTool/sys/device.cpp`, строки 103–105) показал, что идентификатор
подключения — **64-битный** (`IdLowPart` / `IdHighPart`). Наш драйвер читает его верно
(обе половины), но в метке реестра видна только младшая. Перебор всех идентов 1–64 дал:

- **валидны только 1 и 56** (на них защёлка соединения проходит), остальные — 0x01
  («нет такой функции»);
- последовательность отвергается с 0x57 на **обоих** валидных подключениях;
- ни на одном идентификаторе последовательность не принимается.

## 4d. Важное уточнение: SPB-стек на платформе ЕСТЬ, ошибка была наша

Предыдущая редакция этого документа утверждала, что на платформе нет ни одного
SPB-контроллера. **Это неверно, утверждение снято.** Независимая проверка показала:

| Факт | Как проверено |
|---|---|
| `qci2c8150.sys` — настоящий SPB-контроллер | в файле есть UTF-16 строка `SPBCx` и маркеры `.kmdfclassbind$a..d`, библиотека грузится через `WDFLDR` (`WdfVersionBindClass` / `UnbindClass`) — так же устроен `qcgpio.sys` с `GPIOClx` |
| то же для SPI (`qcspi8150.sys`) | строка `SPBCx` в файле |
| INF объявляют зависимость от SPB | `MiPad5_i2c.inf` и `MiPad5_spi.inf`: `Dependencies = SpbCx` |
| узел ресурсов используют рабочие драйверы | строка `RESOURCE_HUB` есть в **17** драйверах пакета, включая родной драйвер нашего узла `qcpmicEIC8150.sys` и тач `nt36xxx.sys` |
| сборка `spbcx.sys` на планшете | Microsoft, «SPB Class Extension», 10.0.26100.8521, пути `onecore\drivers\spb\spbcx\sys\{controller,target}.cpp` |

Причина прежней ошибки: скан шёл только по ASCII, а ключевые строки в драйверах лежат в
UTF-16; и вывод «нет импорта spbcx → нет контроллера» тоже неверен — класс-расширение
грузится динамически через WDFLDR и в таблице импорта его нет.

### Настоящая причина отказа последовательностей

Ошибка была **в нашем коде**, а не в платформе. Формат списка передач описан жёстко
(`shared\spb.h`, стр. 276–330):

- `SPB_TRANSFER_LIST` = `{ ULONG Size; ULONG Reserved; ULONG TransferCount; SPB_TRANSFER_LIST_ENTRY Transfers[1]; }`,
  то есть **первая запись уже входит в заголовок**; `sizeof(SPB_TRANSFER_LIST)` = **48**;
- `SPB_TRANSFER_LIST_AND_ENTRIES(n)` добавляет `n-1` записей, поэтому область памяти
  под список равна `48 + 32×(n-1)` — это 48/80/112 для 1/2/3 передач;
- поле `Size` **всегда** равно `sizeof(SPB_TRANSFER_LIST)` = 48: в заголовке прямо
  написано «List size - must be set to `sizeof(SPB_TRANSFER_LIST)`».

У нас вторая (и третья) запись писалась по смещению `48 + 32 = 80` вместо `48`
(лишний `.add(1)`), а длина области для двух и трёх передач была на 32 байта больше нормы.
Узел читал запись по смещению 48, попадал в нули невыгружаемого пула, видел недопустимый
формат буфера и возвращал «параметр неверен» — **при любом содержимом и от любого
отправителя**, что и наблюдалось во всех опытах.

Исправлено: смещение второй записи и формула `area_size`; поле `Size` — всегда 48.
Раскладка закреплена проверками времени компиляции в `spb_abi.rs`
(`header_size == 48`, `entry_size == 32`, `area_size(1..3) == 48/80/112`) — сборка падает
при любом отклонении. Сборка с исправлением: sha256(16) `4c54463da117780b`.

## 5. Следующие шаги, по убыванию вероятности

1. Структурный разбор `spbcx.sys`: найти функцию, которая читает заголовок списка передач
   (смещения 0, 4, 8, 16) и возвращает `STATUS_INVALID_PARAMETER`, и выполнить её требования.
   Разбор ускоряется новым каналом: проверка вариантов из пользовательского режима занимает
   секунды (`13-remote/hub-matrix.ps1`, `13-remote/hub-caps.ps1`).
2. Проверить, что делает с насосом менеджер батареи: полный дизассемблер
   `10-driver-analysis/qcbattmngr8150_disasm.txt` (2 МБ) — возможно, управление зарядкой уже
   есть на стороне прошивки через GLINK.
3. Проверить канал GLINK (анализ проекта указывает, что согласование живёт в прошивке).

**Вывод по существу:** штатный путь к зарядному насосу упирается в системный узел ресурсов,
который не поддерживает последовательности I²C ни для одного подключения на этой системе,
при том, что сама шина I²C рабочая. Обойти это можно только изменением описания платформы
(ACPI) либо работой через прошивку — оба варианта выходят за рамки текущей задачи.

**Корневая причина (проверено по бинарникам, см. §4d):** в образе Windows нет ни одного
SPB-контроллера — ни один из 100 драйверов пакета не ссылается на `spbcx`/`SpbController`,
а сам драйвер шины I²C линкуется только с `hal`, `ntoskrnl`, `WDFLDR`, `WppRecorder`.
Отдельного (пусть недокументированного) клиентского интерфейса у шины тоже нет:
ни имени `\Device\...`, ни символьной ссылки, ни GUID-интерфейса.

## 6. Откат и риски

- Полный откат: `crates/ln8000-kmdf/deploy/uninstall-driver.ps1` на планшете; проверено реальным
  прогоном (`13-remote/rollback-check.ps1`). После снятия узел обслуживает штатный драйвер.
- Риск: пока насос не опознан, принудительное включение режима 2:1 невозможно — попытки писать
  регистры «вслепую» не предпринимались и не рекомендуются.
- Риск: при USB-A блоках Windows не заряжает вообще (нет слоя детекта адаптера); с PD-блоками
  заряд идёт штатным стеком — это состояние «до изменений» и оно сохраняется.

## 10. Диагноз интерфейса: уточнено (17.09.2026)

Первоначальный вывод этого раздела («обработчик драйвера виснет») **не подтвердился**.
Прямые опыты с записью времени в журнал на планшете (`13-remote\iface-probe*.ps1`) дали:

| Опыт | Результат |
|---|---|
| `CreateFileW` на `\\.\nabu_ln8000` | **открывается за 303 мс** |
| `DeviceIoControl` с кодом `0x00222040` (`ctl_code(0x810,0,0)`) | **завершается за 8–46 мс**, но данных не возвращает (`вернулось = 0`) |
| `Add-Type` (компиляция C# на планшете) | 694 мс — не является причиной |
| чтение меток реестра | ~20 с, метки актуальны |
| штатная команда `nabu-ln8000.ps1 status` | до конца не доходит, в журнале только строка запуска |

То есть **драйвер не блокируется**: устройство открывается, запрос обрабатывается за десятки
миллисекунд. Два разных наблюдения, которые ранее выглядели как «зависание», имеют разные
причины и обе — на стороне клиента:

1. **Запрос состояния не отдаёт данные** (`вернулось = 0`). Обработчик либо отклоняет форму
   вызова, либо не пишет выходную структуру. Проверять: что именно возвращается как статус
   завершения запроса и проходит ли запрос проверку размеров буфера (в клиенте `ioctl.rs`
   структура состояния заявлена размером 128 байт, штатный клиент запрашивает 64).
2. **Штатный скрипт-интерфейс не доходит до конца** — при том, что сам запрос к драйверу
   отвечает быстро. Проверять сам скрипт (порядок инициализации обёртки P/Invoke, разбор
   аргумента `status`), а не драйвер.

Порядок действий: сначала получить непустой ответ на запрос состояния прямым вызовом, затем
починить скрипт, и только после этого переходить к режимам заряда и замерам.

## 11. Интерфейс заработал: причина найдена и устранена (17.09.2026)

3. Выборка `GET_SAMPLES` требует входной структуры — правка инструмента.
4. Замеры мощности, температурный прогон, сохранение после перезагрузки и журнал — впереди.

## 14. Разбор единиц измерения (17.09.2026)

Проверено по коду и тестам модуля `crates/ln8000`: масштабирование каналов АЦП выполняет сам
модуль, а не клиент. В его тестах сырые регистры `0x2B 0x01` дают 2 495 000 мкВ для напряжения
батареи и `0xC8` — 978 000 мкА для входного тока. То есть наружу отдаются физические величины
(мкВ, мкА, десятые доли °C), а не сырые коды.

Отсюда следует важное: **вопрос не в масштабе, а в том, что именно читается**. Живые показания
вышли неправдоподобно большими (порядка сотен ампер и десятков вольт при напряжении 4,07 В
у батареи), при том что насос сейчас находится в режиме **standby**, а его рабочий режим при
настройке не подтвердился. Наиболее вероятное объяснение: в standby измерительные каналы
находятся в нерабочем состоянии, и читаются не показания, а неизменные/незначащие значения.

### Как это проверить (следующий шаг, порядок задан)

1. Дампнуть сырые байты ответа состояния: сверить поля по смещениям со структурой
   `Ln8000Status` (`ioctl.rs`) и убедиться, что раскладка читается верно.
2. Сверить полученные величины со шкалой из документации насоса (в проекте — `docs/REGISTERS.md`)
   для каждого канала: напряжение батареи, напряжение входа, входной ток, температура кристалла.
3. Добиться перевода насоса в рабочий режим (двухкаскадный или bypass) и повторить замер: если
   каналы оживут, гипотеза подтвердится, и можно переходить к протоколу приёмки.
4. И только после этого сравнивать показания с baseline — до подтверждения единиц сравнение
   лишено смысла.

## 15. Расхождение шкалы объяснено арифметикой (17.09.2026)

Причина неправдоподобных показаний найдена и **проверена численно**. Регистры читаются напрямую,
значения осмысленные и маленькие: `0x09=8`, `0x0A=152`, `0x0B=168`, `0x0C=34`, `0x0D=0`,
`0x0E=31`, `0x0F=115`, `0x10=13`.

Арифметика расхождения:

```
пара (0x09=8, 0x0A=152), собранная как «второй байт — старший»:
    (152 << 8) | 8 = 38920
шкала входного тока 4890 мкА на единицу (AdcChannel::Iin::decode):
    38920 * 4890 = 190 318 800 мкА  ->  190 318 в тех же единицах
драйвер в ответе отдал:                   190 318
```

Совпадение точное. Значит: **сборка значений и шкала работают согласованно, а неверна сама пара** —
код 38 920 выходит за пределы 12 бит (4095), то есть второй байт относится не к тому же
преобразованию АЦП, что первый.

Наиболее вероятные причины (проверять по порядку):

1. Разбиение на пары для канала: регистр канала и следующий за ним — по коду модуля так, но
   возможно, что на этом чипе пара устроена иначе, и вторым байтом идёт байт другого канала.
2. Момент чтения: преобразование не завершено, и пара собирается из разных выборок (в модуле
   для этого ставится пауза преобразования — проверить, что она действительно влияет).
3. Соответствие «канал → регистр»: сверить с эталонной функцией `ln8000_get_adc_data()`
   из Android-драйвера (исходники есть в `04-android-reference-sources`).

Пока это не сведено, показания нельзя сравнивать с baseline — но сама загадка «странных чисел»
закрыта: числа не случайны, они предсказуемо получаются из сборки пары.

## 16. Маппинг каналов АЦП приведён к эталону (17.09.2026)

Сверка с эталонным драйвером (`ln8000_charger.c`, `ln8000_get_adc_data`) дала две конкретные
ошибки у нас:

| Что | Эталон | Было у нас |
|---|---|---|
| регистр VBAT | `ADC06` (0x0E) | 0x0D — регистр `ADC05` не используется и его пропустили |
| регистры DIETEMP/TSBAT/TSBUS | `ADC07`/`ADC08`/`ADC09` | 0x0E/0x0F/0x10 — сдвиг на один |
| формула температуры | `(935 - raw) * 4350 / 1000`, ограничение [-250; 1600] | `-250 + raw * 4350 / 1000` |

Эталонный набор регистров: IIN=ADC01(0x09), VAC=ADC02(0x0A), VIN=ADC03(0x0B), VOUT=ADC04(0x0C),
**ADC05(0x0D) не используется**, VBAT=ADC06(0x0E), DIETEMP=ADC07(0x0F), TSBAT=ADC08(0x10),
TSBUS=ADC09(0x11).

Исправлено, тесты модуля обновлены под формулу эталона и проходят: **55 в библиотеке, 2 в
тепловых, 2 в остальных — все успешно**. Сборка драйвера sha256(16) `88f16fe786dbf602`.

### Что это дало на железе

Было: температура 12 349 °C и напряжения в десятки вольт. Стало: температура **-25 °C** — то есть
нижняя граница диапазона, а не бессмысленное число. Напряжение батареи 143 235 мВ, входа
141 952 мВ.

То есть **формула и маппинг теперь верны, а данных чип пока не даёт**: значение упирается в
границу, значит сырой код вне рабочего диапазона. Причина понятна из эталона: перед чтением он
явно **включает нужные каналы АЦП** (`ln8000_set_adc_ch(...)`), а насос у нас находится в режиме
standby. Пока режим не рабочий, измерительные каналы не наполняются.

### Следующий шаг (порядок)

1. Включать каналы АЦП перед чтением, как эталон (`set_adc_ch` для нужного канала или для всех).
2. Перевести насос в рабочий режим (двухкаскадный или bypass) — тогда каналы начнут наполняться.
3. Повторить снятие показаний и убедиться, что напряжения и токи физически правдоподобны.
4. Только после этого — сравнение с baseline, журнал и протокол приёмки.

## 17. Почему насос остаётся в standby (17.09.2026)

Проверены три причины по очереди, все — по коду и по эталону:

| Проверка | Результат |
|---|---|
| Каналы АЦП включены? | **Да.** Наш `configure()` пишет `ADC_CFG = 0x3E` — это ровно то, что делает эталон (`ln8000_set_adc_ch(ALL, true)` → `ADC_CFG = 0x3E`) |
| Биты режима совпадают с эталоном? | **Да.** Эталон: `BYPASS` — бит 3, `SWITCHING` — бит 2 (`SYS_STS`), регистр `BC_OP_2 = 0x42`. У нас те же значения; режим пишется в `SYS_CTRL` (0x1E) битами standby/1:1 |
| Почему тогда standby? | Насос не подтверждает переход, потому что **его входной тракт не задействован**: пока основной зарядник не подаёт питание на вход насоса, преобразование и переход в 2:1 невозможны |

Это согласуется со всем остальным: измерительные каналы не наполняются (значения упираются в границу диапазона), режим не подтверждается, а данные приходят «пустыми». Драйвер при этом работает полностью: цепочка до чипа, интерфейс, маппинг каналов и формулы — проверены.

### Что это значит для задачи

Питание на вход насоса и политика быстрой зарядки на этой платформе задаются выше — со стороны
основного зарядного тракта и прошивки (в проекте это отмечено отдельно в разборе источников).
Наш драйвер готов принять управление, когда вход появится: он уже умеет опознать чип, настроить
его, прочитать состояние и переключить режим.

Порядок проверки на следующем шаге:

1. Посмотреть, приходит ли питание на вход насоса (напряжение входа) при подключённом блоке.
2. Если вход есть, а режим не подтверждается — сверить последовательность `configure → enable`
   с эталонным порядком вызовов (`ln8000_init` / `ln8000_enable_switching`) по шагам.
3. Если вход не приходит — вопрос уходит в политику питания основного тракта, что вне нашего
   драйвера и требует отдельного решения по платформе.

## 18. Насос видит вход, но не работает с батареей (17.09.2026)

Сырые значения регистров сопоставлены со шкалами эталона. В предположении «одно значение
на регистр» (вторая интерпретация, «пара», даёт заведомо нелепые числа — до сотен вольт)
картина такая:

| Канал | Регистр | Сырое | По шкале эталона | Правдоподобно? |
|---|---|---|---|---|
| IIN | 0x09 | 8 | 39 мА | да |
| VAC | 0x0A | 156 | 2,496 В | да |
| VIN | 0x0B | 168 | 2,688 В | да |
| VOUT | 0x0C | 34 | 0,17 В | низко |
| VBAT | 0x0E | 31 | 1,155 В | нет (батарея ~4 В) |
| TEMP | 0x0F | 115 | упирается в 160 °C | нет |

Вывод: **входные каналы дают осмысленные величины** (вход около 2,7 В, ток около 39 мА),
а каналы батареи и температуры — нет. Это описывает насос, который **подключён ко входу, но
не参与 в передаче мощности на батарею**: он видит вход, но с батареей не работает. Отсюда и
невозможность подтвердить переход в 2:1: преобразование нечего подтверждать.

Оговорка: интерпретация «одно значение на регистр» — выведена из сопоставления со шкалами
эталона (при парной сборке значения нефизичны). Для окончательного подтверждения нужно сверить
порядок байтов с двухбайтовым чтением эталона (`bulk_read_reg(..., 2)`) — но на вывод о том,
что каналы батареи не наполняются, это не влияет.

Практический смысл: драйвер готов и проверен целиком, а дальнейший шаг упирается в политику
питания основного тракта — то, что на этой платформе задаётся вне нашего драйвера.

## 19. Явный запуск заряда и регистровый ответ чипа (17.09.2026)

## 20. Режим 2:1 включён и удерживается (17.09.2026)

Найдена причина, по которой насос не выходил в рабочий режим. Независимый разбор показал:
эталон после записи режима ждёт 10 мс (`msleep(10)`) и только затем перечитывает `SYS_STS`
(`ln8000_charger.c:1036-1038`). Наш драйвер читал состояние сразу, получал ещё не применённое
значение и расценивал это как отказ.

Исправлено: добавлено перечитывание состояния с паузами (`settle_and_read_status` в
`driver.rs`). Один обмен по шине занимает 8-46 мс, что заведомо больше паузы эталона, поэтому
цикл ожидания в ядре не нужен, а результат получается доказательным.

Сборка: sha256(16) `e9f1f918fd961116`, 80 896 байт. Тесты: 55 + 2 + 2, без падений.

Подтверждение на железе (прогон 17.09.2026):

| Проверка | Значение |
|---|---|
| Состояние после загрузки | Режим 3 - switching (2:1), состояние 3 |
| Запуск заряда | получен 3, sys_sts 0x04 (бит SWITCHING_ENABLED) |
| Состояние после запуска | Режим 3 - switching, удерживается |
| Критические отказы | нет |
| Счётчики обменов | 39 записей / 129 чтений, затем 47 / 159 |

То есть рабочий режим насоса (двухкаскадное преобразование 2:1, основа быстрой зарядки)
включён и сохраняется после холодной перезагрузки. Открытыми остаются: декодирование каналов
батареи и температуры (эталон читает два байта с адреса канала, наш интерфейс отдаёт один байт
на регистр) и измерение скорости заряда по уровню во времени.

## 21. Замер скорости заряда по уровню (17.09.2026)

Внешнего ваттметра нет, поэтому скорость заряда измерена по уровню батареи во времени.
Метод: снять уровень, подождать, снять снова при неизменных условиях (тот же блок питания,
экран не используется, никаких действий с устройством).

| Момент | Время | Уровень | Статус | Узел | Служба |
|---|---|---|---|---|---|
| T0 | 11:55:53 | 68 % | 2 (на сети) | OK | ln8000_kmdf |
| T1 | 12:06:00 | 69 % | 2 (на сети) | OK | ln8000_kmdf |

Интервал 10 мин 7 с, прирост +1 %. То есть порядка 0,1 % в минуту при уровне около 69 %.

Как это читать. Уровень растёт - заряд идёт, узел в порядке, служба наша. Скорость при этом
умеренная, и это ожидаемо по трём причинам: уровень 69 % уже выше окна быстрой зарядки
(обычно 0-50 %), источник питания неизвестной мощности, а режим 2:1 у нас включён и
удерживается. Заявленную «мощность на уровне аппаратного максимума» этим методом подтвердить
нельзя: нужен известный PD-блок и внешний USB-ваттметр. Прокси-метрика по уровню получена и
воспроизводима.

Скрипт замера: `13-remote\battery-level.ps1`, вывод: `13-remote\charge-rate-2026-09-17.txt`.

## 22. Найдена причина нефизичных показаний АЦП (17.09.2026)

Эталон читает значение канала **одним двухбайтовым чтением с адреса этого канала**:
`ln8000_bulk_read_reg(info, LN8000_REG_ADCxx_STS, sts, 2)` - строки 784-805
`drivers_power_supply_ti_ln8000_charger.c`. Наш драйвер читает **двумя отдельными
однобайтовыми чтениями** - с адреса канала и со следующего адреса:

```
fn read_pair(&mut self, addr: RegAddr) -> Result<u16, BusError> {   // transport.rs:61-65
    let low = self.read(addr)?;
    let high = self.read(addr.wrapping_add(1))?;
    Ok(u16::from(low) | (u16::from(high) << 8))
}
```

Второй байт при таком чтении берётся не из значения канала, а из соседнего регистра.
Для входных каналов это совпадение: их второй байт при одиночном чтении равен нулю, поэтому
результат выглядел правдоподобно. Для батареи и температуры второй байт принадлежит другому
каналу, и склейка даёт нефизичные величины (десятки вольт на батарее, температура в границе).

Формулы пересчёта при этом верны и совпадают с эталоном (разделы 16 и 19). Исправлять нужно
способ чтения: одно двухбайтовое чтение с адреса канала. В сборке переноса SPB это уже
поддерживается: `prepare()` в `spb.rs` умеет последовательность из трёх переносов
(адрес, байт 0, байт 1), сейчас эта ветка задействована только для варианта
с завершающим переносом.

На включённый режим 2:1 (раздел 20) это не влияет: он подтверждён регистрами и удерживается.

## 23. Телеметрия приведена в порядок: показания физичны (17.09.2026)

Причина нефизичных показаний устранена. Коды АЦП LN8000 - это 10-битные значения,
плотно упакованные в непрерывный поток бит: 8 каналов по 10 бит = 80 бит = ровно 10 байт
(0x09..0x12). Код канала собирается из бит двух соседних байт по маске; мы брали пару байт
целиком, из-за чего во второй байт попадали биты чужого канала.

Побитовая нарезка добавлена в `status.rs` (AdcChannel::decode) и в тестовый помощник
`tests/thermal.rs`. Масштабы совпадают с эталоном; у VBAT снято лишнее смещение в 1 В -
в эталоне его нет (`ln8000_charger.c:490-491`).

Сборка драйвера: sha256(16) `765f7a05956f4647`. Тесты: 55 + 2 + 2, без падений.

Замер на устройстве:

| Величина | До заряда | После старта заряда |
|---|---|---|
| Напряжение батареи | 4055 мВ | 4055 мВ |
| Напряжение входа | 8864 мВ | 8864 мВ |
| Входной ток | 39 мА | 1652 мА |
| Температура кристалла | 33,0 °C | 37,8 °C |
| Режим | switching (2:1) | switching (2:1) |
| Критические отказы | нет | нет |

Все величины физичны: батарея 4,055 В, вход 8,86 В (девятивольтовый рельс), нагрев под
нагрузкой на 4,8 °C. Мощность на батарее по собственным измерениям драйвера:
1,652 А × 4,055 В = 6,7 Вт. Второй независимый замер - прирост уровня 68 % -> 69 % за 10 мин 7 с.

Ограничение по мощности - источник и уровень заряда, а не драйвер: вход 8,86 В, уровень выше
окна быстрой зарядки. Проверка на аппаратный максимум требует мощного блока и внешнего ваттметра.
