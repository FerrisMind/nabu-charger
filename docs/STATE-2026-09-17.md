# Work status: charging and fast charging on nabu (Windows)

Date: 2026-09-17. Written up from the results of working with the tablet over SSH.

> **Superseded in part.** This page is a snapshot of 17.09, before the access path to the
> node was resolved. Its headline claim — "charging under Windows does not work" — no
> longer holds: the LN8000 driver is installed and the tablet fast-charges from a Quick
> Charge brick (measured 21.09: SoC 44 → 85 %, `Iin` up to 1.6 A). The diagnosis below,
> the `STATUS_INVALID_PARAMETER` rejection in particular, is kept because it documents
> what was ruled out and how. For the current state see the project status section of the
> [README](../README.md) and [FINDINGS.md](FINDINGS.md).

## 1. In short

- The software part (driver, package, profiles, telemetry, journal, protection, documentation,
  reproducible signed build) - is ready and verified.
- The driver installs and loads, the device is created, the bus opens,
  the connection resource is parsed, requests to the node go out.
- **Charging under Windows does not work.** The LN8000 charge pump is not recognised: the system
  connection object (`\Device\RESOURCE_HUB\<id>`) rejects the I²C sequence request
  with the code `STATUS_INVALID_PARAMETER` (0xC000000D) for any form of the request.

## 2. What is established with certainty (with evidence)

| Fact | Evidence |
|---|---|
| Chip at I²C 0x51, bus QUPv3 SE4 = ACPI `I2C5` | device tree `ln8000_charger@51` in `qupv3_se4_i2c`; ACPI map: `QCOM057E`/`PEIC` on `I2C5` |
| The node has exactly one connection: class SERIAL (2), type I2C (1), id 1 | the `_CRS` resource list in the node registry (`ConnCount`, `C0Class`, `C0Type`, `C0Low`) |
| The path to the node is built correctly | the same path is used by the stock driver (`FUN_14000acd0` in `qcpmicEIC8150.sys`) and the drivers `qcpmictcc8150`/`qcusbcucsi8150` |

| The node rejects sequences | `IOCTL_SPB_EXECUTE_SEQUENCE` → 0xC000000D for 10+ variants of the request form |

| The stock driver for the node does not get through on this system either | its attach request `0x32C004` to the parent → `0xC0000003`/`0xC0000034`; to the node → 0xC0000010 |

## 3. What has been checked and ruled out on the request layout

Transfer list size (48/80/112 bytes), the semantics of the `Size` field (header versus full length),
placement of the data (in the transfer area / in the data buffer / in the passed output buffer),
buffer format (`Simple`, `SimpleNonPaged`), a terminating entry with direction `None`,
presence and absence of an output buffer, the access mask used to open the node
(`GENERIC_READ|GENERIC_WRITE` and, as with the stock driver, `0x1F01FF`), holding the connection,
synchronous and asynchronous submission. The outcome is the same - `0xC000000D`.

## 4. Where the unknown remains

The check inside the system connection object. It is created by the SPB system library
(`spbcx.sys`; it contains the string `RESOURCE_HUB` and the object `SPBCLIENT`). The library has no
trace strings for the transfer list check, so it has to be found structurally - by looking at the
accesses to the fields of the list header, not by searching for a constant.

## 4a. New: the node has been probed from user mode (a fast channel)

The node `\Device\RESOURCE_HUB\0000000000000001` **opens from user mode** and
accepts requests. This gives a check channel that takes seconds, without reboots. The resulting matrix:

| Bus request | Without buffers | With a transfer list |
|---|---|---|
| Controller acquire | not supported (0x32) | not supported |
| Controller release | not supported (0x32) | not supported |
| Sequence | **requires a buffer (0x7A)** | invalid parameter (0x57) |
| Connection lock | 0x16 | 0x16 |
| Connection unlock | **supported** | 0x16 |
| Full duplex | no such function (0x01) | no such function |
| Special | no such function (0x01) | no such function |

What this proves:

1. The node **parses** the sequence request - without a buffer it explicitly asks for a buffer (0x7A),
   so the handler exists and the route is correct.
2. With a buffer present it rejects the contents (0x57) - and does so **for any contents**:
   with a zero header size, with a zero transfer count, with different directions and formats,
   with an input length of 48/56/64/80, before and after locking the connection. So this is not a
   layout mistake on our side: the frame matches what the stock driver writes.
3. The node implements only the **connection** level (lock/unlock); it has no controller
   level (0x32) - it is a resource node, not a full bus intermediary.

## 4b. New: where the node sits in the device tree

The parent of our node is the **ACPI bus** (`ACPI_HAL\PNP0C08\0`), not the I²C controller. This is
the standard arrangement for devices described in ACPI with a connection resource: the client has to go
through the resource node. So the chosen route is correct, and the blocker is the node itself.

## 4c. New: the node's `_CRS` has been decoded and all connections checked

In the live DSDT dump (`09-acpi-nabu/live-dump/acpi-dump/DSDT_explicit.dsl`, 3.2 MB, 78 758 lines)
the `PEIC` device has been taken apart down to the bytes. Its `_CRS` is a connection descriptor (type `0x8E`,
length 25), with the following written directly inside:

- the device address **`0x51`** - the LN8000 address;
- the controller name **`\_SB.I2C5`** - the very bus that runs in the system as
  `ACPI\QCOM0511\5` (state OK, service `qci2c`).

The strings `LN8000` / `LIONSEMI` are completely absent from the dump - the node is described generically,
which is why it is not recognised by name.

Bus state in the system (one request instead of a hundred):

| Bus | Devices | State | Service |
|---|---|---|---|
| I²C (QUPv3) | `ACPI\QCOM0511\1`, `\5`, `\8` | OK, code 0 | `qci2c` |
| SPMI | `ACPI\QCOM050C\1` | OK, code 0 | `qcspmi` |
| SPI | `ACPI\QCOM050F\4`, `\13` | OK, code 0 | `qcspi` |

So the **I²C bus is alive**, and the node in an error state is the only one on the tablet (of 108
`ACPI\QCOM*` devices, 107 have no problems).

### Enumerating connection identifiers

Microsoft's sample (`SpbTestTool/sys/device.cpp`, lines 103-105) showed that the connection
identifier is **64-bit** (`IdLowPart` / `IdHighPart`). Our driver reads it correctly
(both halves), but only the low half is visible in the registry mark. Enumerating all identifiers 1-64 gave:

- **only 1 and 56 are valid** (the connection lock succeeds on them), the rest return 0x01
  ("no such function");
- the sequence is rejected with 0x57 on **both** valid connections;
- on no identifier is the sequence accepted.

## 4d. Important correction: the SPB stack IS present on the platform, the mistake was ours

A previous revision of this document claimed that the platform has no
SPB controller at all. **This is wrong, the claim is withdrawn.** An independent check showed:

| Fact | How it was checked |
|---|---|
| `qci2c8150.sys` is a real SPB controller | the file contains the UTF-16 string `SPBCx` and the markers `.kmdfclassbind$a..d`, the library loads through `WDFLDR` (`WdfVersionBindClass` / `UnbindClass`) - `qcgpio.sys` with `GPIOClx` is built the same way |
| the same for SPI (`qcspi8150.sys`) | the string `SPBCx` in the file |
| the INF files declare a dependency on SPB | `MiPad5_i2c.inf` and `MiPad5_spi.inf`: `Dependencies = SpbCx` |
| the resource node is used by working drivers | the string `RESOURCE_HUB` is present in **17** drivers of the package, including the native driver of our node `qcpmicEIC8150.sys` and the touch driver `nt36xxx.sys` |
| the build of `spbcx.sys` on the tablet | Microsoft, "SPB Class Extension", 10.0.26100.8521, paths `onecore\drivers\spb\spbcx\sys\{controller,target}.cpp` |

The cause of the earlier mistake: the scan was ASCII-only, while the key strings in the drivers are
in UTF-16; and the conclusion "no spbcx import → no controller" is wrong too - the class extension
loads dynamically through WDFLDR and is not in the import table.

### The real cause of the sequence failures

The mistake was **in our code**, not in the platform. The transfer list format is defined strictly
(`shared\spb.h`, pp. 276-330):

- `SPB_TRANSFER_LIST` = `{ ULONG Size; ULONG Reserved; ULONG TransferCount; SPB_TRANSFER_LIST_ENTRY Transfers[1]; }`,
  that is, **the first entry is already part of the header**; `sizeof(SPB_TRANSFER_LIST)` = **48**;
- `SPB_TRANSFER_LIST_AND_ENTRIES(n)` adds `n-1` entries, so the memory area
  for the list equals `48 + 32×(n-1)` - that is 48/80/112 for 1/2/3 transfers;
- the `Size` field is **always** equal to `sizeof(SPB_TRANSFER_LIST)` = 48: the header says so
  directly, "List size - must be set to `sizeof(SPB_TRANSFER_LIST)`".

In our code the second (and third) entry was written at offset `48 + 32 = 80` instead of `48`
(a superfluous `.add(1)`), and the area length for two and three transfers was 32 bytes above the norm.
The node read the entry at offset 48, landed in zeros of the non-paged pool, saw an invalid
buffer format and returned "invalid parameter" - **for any contents and from any
sender**, which is what was seen in every experiment.

Fixed: the offset of the second entry and the `area_size` formula; the `Size` field is always 48.
The layout is pinned by compile-time checks in `spb_abi.rs`
(`header_size == 48`, `entry_size == 32`, `area_size(1..3) == 48/80/112`) - the build fails
on any deviation. Build with the fix: sha256(16) `4c54463da117780b`.

## 11. The interface started working: the cause found and fixed (17.09.2026)

The cause of the control request failures is **one field in the queue configuration**. The WDK header
shows how the default queue differs (`Include\wdf\kmdf\1.15\wdfio.h`):

```c
WDF_IO_QUEUE_CONFIG_INIT_DEFAULT_QUEUE(Config, DispatchType) {
    Config->DefaultQueue = TRUE;      // line 443
    Config->DispatchType = DispatchType;
}
```

In our code the configuration was assembled by hand and the `DefaultQueue` flag was not set. A queue that
is not declared as the default queue **does not receive control requests**: they are picked up by the
default WDF queue and completed with `STATUS_INVALID_DEVICE_REQUEST`, which the client sees as error
code **1** (`ERROR_INVALID_FUNCTION`). That is exactly what the tool on the tablet showed - on all
four requests in a row, which became the decisive clue.

Fix: `DefaultQueue = TRUE` added to the queue configuration. Build sha256(16)
`b0561c13bb0262c8`.

## 14. Analysis of the units (17.09.2026)

Checked against the code and tests of the `crates/ln8000` module: the scaling of the ADC channels is done by the
module itself, not by the client. In its tests the raw registers `0x2B 0x01` give 2 495 000 µV for the battery
voltage and `0xC8` - 978 000 µA for the input current. So physical quantities
(µV, µA, tenths of °C) are handed out, not raw codes.

An important point follows: **the question is not the scale but what exactly is being read**. The live readings
came out implausibly large (on the order of hundreds of amperes and tens of volts with the battery
at 4.07 V), even though the pump is currently in **standby** mode and its working mode was not
confirmed during configuration. The most likely explanation: in standby the measurement channels
are not working, and what is read is not readings but fixed/insignificant values.

### How to check this (next step, order is fixed)

1. Dump the raw bytes of the state response: cross-check the fields by offset against the
   `Ln8000Status` structure (`ioctl.rs`) and make sure the layout is read correctly.
2. Cross-check the values obtained against the scale from the pump documentation (in the project - `docs/REGISTERS.md`)
   for each channel: battery voltage, input voltage, input current, die temperature.
3. Get the pump into a working mode (two-stage or bypass) and repeat the measurement: if

4. And only after that compare the readings with the baseline - before the units are confirmed the comparison

## 15. The scale discrepancy explained by arithmetic (17.09.2026)

The cause of the implausible readings has been found and **verified numerically**. The registers are read directly,
the values are meaningful and small: `0x09=8`, `0x0A=152`, `0x0B=168`, `0x0C=34`, `0x0D=0`,
`0x0E=31`, `0x0F=115`, `0x10=13`.

The arithmetic of the discrepancy:

```
the pair (0x09=8, 0x0A=152) assembled as "second byte is the high one":
    (152 << 8) | 8 = 38920
input current scale 4890 µA per unit (AdcChannel::Iin::decode):
    38920 * 4890 = 190 318 800 µA  ->  190 318 in the same units
driver returned in the response:          190 318
```

The match is exact. So: **the value assembly and the scale work consistently, and the pair itself is wrong** -
the code 38 920 is beyond the 12-bit range (4095), that is, the second byte does not belong to the same
ADC conversion as the first.

The most likely causes (check in order):

1. The pairing for a channel: the channel register and the one after it - that is how the module code has it, but
   it is possible that on this chip the pair is arranged differently, and the second byte is the byte of another channel.
2. The read timing: the conversion is not complete and the pair is assembled from different samples (the module
   sets a conversion pause for this - check that it really has an effect).
3. The "channel → register" correspondence: cross-check against the reference function `ln8000_get_adc_data()`
   from the Android driver (the sources are in `04-android-reference-sources`).

Until this is reconciled, the readings cannot be compared with the baseline - but the riddle of the "strange numbers"
itself is closed: the numbers are not random, they are predictably produced by the pair assembly.

## 16. ADC channel mapping brought in line with the reference (17.09.2026)

The cross-check against the reference driver (`ln8000_charger.c`, `ln8000_get_adc_data`) revealed two specific
mistakes on our side:

| What | Reference | What we had |
|---|---|---|
| VBAT register | `ADC06` (0x0E) | 0x0D - the `ADC05` register is unused and was skipped |
| DIETEMP/TSBAT/TSBUS registers | `ADC07`/`ADC08`/`ADC09` | 0x0E/0x0F/0x10 - shifted by one |
| temperature formula | `(935 - raw) * 4350 / 1000`, clamp [-250; 1600] | `-250 + raw * 4350 / 1000` |

The reference register set: IIN=ADC01(0x09), VAC=ADC02(0x0A), VIN=ADC03(0x0B), VOUT=ADC04(0x0C),
**ADC05(0x0D) is unused**, VBAT=ADC06(0x0E), DIETEMP=ADC07(0x0F), TSBAT=ADC08(0x10),
TSBUS=ADC09(0x11).

Fixed, the module tests were updated for the reference formula and pass: **55 in the library, 2 in the
thermal ones, 2 in the rest - all successful**. Driver build sha256(16) `88f16fe786dbf602`.

### What this gave on hardware

Before: temperature 12 349 °C and voltages in the tens of volts. After: temperature **-25 °C** - that is,
the bottom of the range rather than a meaningless number. Battery voltage 143 235 mV, input
141 952 mV.

So **the formula and the mapping are now correct, but the chip does not give data yet**: the value hits
the limit, so the raw code is outside the working range. The cause is clear from the reference: before reading it
explicitly **enables the required ADC channels** (`ln8000_set_adc_ch(...)`), while our pump is in
standby mode. While the mode is not a working one, the measurement channels are not filled.

### Next step (order)

1. Enable the ADC channels before reading, as the reference does (`set_adc_ch` for the required channel or for all).
2. Move the pump into a working mode (two-stage or bypass) - then the channels will start to fill.
3. Repeat the readings and make sure the voltages and currents are physically plausible.
4. Only after that - comparison with the baseline, the journal and the acceptance protocol.

The power to the pump input and the fast-charge policy on this platform are set higher up - on the side of
the main charging path and the firmware (this is noted separately in the project's source analysis).

## 18. The pump sees the input but does not work with the battery (17.09.2026)

The raw register values were matched against the reference scales. Under the assumption "one value
per register" (the second interpretation, the "pair", gives obviously absurd numbers - up to hundreds of volts)
the picture is this:

| Channel | Register | Raw | By the reference scale | Plausible? |
|---|---|---|---|---|
| IIN | 0x09 | 8 | 39 mA | yes |
| VAC | 0x0A | 156 | 2.496 V | yes |

## 22. Cause of the non-physical ADC readings found (17.09.2026)

The reference reads a channel value **with a single two-byte read from that channel's address**:
`ln8000_bulk_read_reg(info, LN8000_REG_ADCxx_STS, sts, 2)` - lines 784-805 of
`drivers_power_supply_ti_ln8000_charger.c`. Our driver reads it **with two separate
one-byte reads** - from the channel address and from the next address:

```
fn read_pair(&mut self, addr: RegAddr) -> Result<u16, BusError> {   // transport.rs:61-65
    let low = self.read(addr)?;
    let high = self.read(addr.wrapping_add(1))?;
    Ok(u16::from(low) | (u16::from(high) << 8))
}
```

With this read the second byte comes not from the channel value but from the neighbouring register.
For the input channels this is a coincidence: their second byte is zero on a single read, so the
result looked plausible. For the battery and temperature the second byte belongs to another
channel, and gluing them together gives non-physical quantities (tens of volts on the battery, the temperature at the limit).

The conversion formulas themselves are correct and match the reference (sections 16 and 19). What has to be fixed is
the read method: a single two-byte read from the channel address. The SPB transfer build already
supports this: `prepare()` in `spb.rs` can build a sequence of three transfers
(address, byte 0, byte 1), but at the moment that branch is used only for the variant
with a terminating transfer.

This does not affect the enabled 2:1 mode (section 20): it is confirmed by the registers and holds.

## 23. Telemetry put in order: the readings are physical (17.09.2026)

The cause of the non-physical readings has been eliminated. The LN8000 ADC codes are 10-bit values
tightly packed into a continuous bit stream: 8 channels of 10 bits = 80 bits = exactly 10 bytes
(0x09..0x12). A channel code is assembled from bits of two neighbouring bytes using a mask; we took the byte pair
whole, which is why bits of another channel landed in the second byte.

Bit-level slicing has been added to `status.rs` (AdcChannel::decode) and to the test helper
`tests/thermal.rs`. The scales match the reference; the extra 1 V offset was removed from VBAT -
the reference does not have it (`ln8000_charger.c:490-491`).

## 34. Profile confirmed after a restart: the driver applies the setpoints (15:15-15:30)

**Checking the cause of the discrepancy.** During configuration the driver wrote 3.0 A and 4.35 V instead of the specified 2.7 A and 4.42 V.

## 37. Pump state after driver rebinds: a safe wait (16:00-16:20)

> *Correction 18.09.2026: the cause of the wait (39 mA, standby) is the CV loop at a charge target of 4.42 V, see section 38.*

**What is observed.** After a series of package rebinds (removal, reinstall, `remove-device` +
`scan-devices`, restarts) the pump stays in **standby** state (mode 1): current 39 mA, battery 4.39 V,
die 31.3 °C. Mode requests are rejected: `SET_MODE (2)` → `requested=2 applied=0 driver code=-4`,
`SET_CHARGE (start)` → `requested=switching(3) got=0 pump code=-4`. That is, the configuration gets through (the registers
of our setpoints are in place: `IIN_CTRL = 0x36`, `V_FLOAT_CTRL = 0x8B`, `GLITCH_CTRL = 0x8E`), but the chip does not confirm
that switching started. The fault flags are zero (`sys_sts`, `fault1`, `fault2`, `safety` = 0), and
register reads work (device identifier `0x00` = `0x42`, the ADC registers read).

**What was tried and did not help:** three mode requests in a row (self-healing), a request for the two-stage mode
(1), turning the watchdog off (`WatchdogEnabled = 0`) with a device restart, the tool's full self-test.

**Most likely cause.** The switching mode is enabled by the main PM8150B charger: the pump gets
permission on the input. Driver rebinds and device restarts cause the source to be re-detected
in the PMIC, and its state may not have returned to the previous one. Earlier, before these operations, the same chip in the same pass-through
mode gave 1.4-2.9 A.

**Recovery procedure (one minute, by the user):**
1. Unplug and reconnect the power cable (source re-detection) or reboot the tablet.
2. Check the state: `nabu-probe.exe stat` - `mode: 2 - bypass` and a current of 1.4-2.9 A are expected.
3. If it is waiting again - repeat the cable unplug; the driver writes the profile setpoints itself at every start
(confirmed twice after device restarts).

**Important for acceptance:** the measurements from the fast sessions (15-17 W at 9 V, 12.7 W at 5 V) were taken before these operations and
remain valid as proof of functionality; the current state is a consequence of debug driver rebinds,
not a profile defect.

**A. The SPMI path `\Device\Spmi\SUPERUSER` works.** Sections 35 and 36 claim the opposite ("open

The earlier conclusion referred to an earlier build (that probe enumerated eight access masks);
on build 20.47.10.605 the open succeeds. We do not claim to know the exact cause of the earlier failure.

**B. The APSD byte `0x28` is HVDCP2 (QC 2.0), not "AFC-like 5 V".** The reference table
`04-android-reference-sources\drivers_power_supply_qcom_smb5-lib.c` (around line 565):

```c
[HVDCP2] = {
    .name = "HVDCP2",
    .bit  = DCP_CHARGER_BIT | QC_2P0_BIT,   /* 0x08 | 0x20 = 0x28 */
    .pst  = POWER_SUPPLY_TYPE_USB_HVDCP
},
```

where `QC_2P0_BIT = BIT(5)` (`drivers_power_supply_qcom_smb5-reg.h:222`), `DCP_CHARGER_BIT = BIT(3)`.
The earlier driver logic (`apsd_is_afc_like_5v`) treated `0x28` as the sign of "an AFC charger that does not
raise the voltage" and took such a charger to 5 V bypass without issuing `FORCE_9V`. This rejected
real QC 2.0 chargers. Fixed on 18.09.2026: `0x28` goes down the QC2 `FORCE_9V` branch; the transition to 5 V bypass
remains only as a fallback if the voltage really does not rise.

**C. The AFC protocol is absent on nabu.** Zero matches for `afc` across the device tree, the kernel and
`hvdcp_opti` in `04-android-reference-sources\` and `16-firmware-extract\`. Therefore the Samsung TA220 (AFC)
can only be served as an ordinary DCP source at 5 V with a raised current, not through AFC negotiation.

**D. The charge target voltage for a full charge is 4.45 V, not 4.42 V.**

| Quantity | Value | Source |
|---|---|---|
| Full charge target (setpoint) | 4.45 V | registry, `VbatFloatUv` |
| Register limit | 4.47 V | `V_FLOAT_CTRL` |
| QC3 mode ceiling | 4.42 V | `mi,qc3-bat-volt-max`, nabu device tree |

4.42 V is the ceiling **for QC3 mode only**, not the full charge target. Encoding of
`V_FLOAT_CTRL`: code = (mV − 3725) / 5, hence 4420 mV = 139 = `0x8B`; 4450 mV = 145 = `0x91`;
4470 mV = 149 = `0x95`.

Why this matters (the symptom "on Windows it charges more slowly than on Android"): with a target of 4.42 V the pump
ran into its own CV limit while the battery was already 4.39-4.49 V, the `VFLOAT_LOOP` loop
became active (bit 6 of the `SYS_STS` register), and the current dropped to 39 mA - the top part of the charge was in effect
not charging. This also explains the state in section 37: in the record `qc35-post_2026-09-18_001305`
`sys_sts = 0x44` (bit 6 raised - `VFLOAT_LOOP`), current 39 mA with the battery at 4390 mV.
