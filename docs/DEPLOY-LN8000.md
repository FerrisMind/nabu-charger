# LN8000: развёртывание, диагностика, откат

Практическое руководство по драйверу charge pump LN8000 для планшета
Xiaomi Pad 5 (`nabu`) под Windows on ARM64.

Связанные документы: [LN8000.md](LN8000.md) (карта регистров и режимы),
[ARCHITECTURE.md](ARCHITECTURE.md), [HANDOVER.md](HANDOVER.md).

---

## 1. Что ставим и куда

| Компонент | Путь | Назначение |
|---|---|---|
| Драйвер | `crates/ln8000-kmdf` → `ln8000_kmdf.sys` + `.inf` + `.cat` | управляет LN8000 на узле ACPI `PEIC` |
| Готовый пакет | `artifacts/driver-ln8000-arm64/` | то, что копируется на планшет |
| Скрипты развёртывания | `crates/ln8000-kmdf/deploy/` | установка, обновление, удаление, диагностика |

Узел `PEIC` (`_HID = QCOM057E`, I²C 0x51 на `\_SB.I2C5`, `_STA = 0x0F`) **уже
описан в DSDT планшета** — правки ACPI и перепрошивка UEFI не нужны. Драйвер
встаёт на существующий `_HID`.

## 2. Сборка

```powershell
rustup target add aarch64-pc-windows-msvc
cargo install cargo-wdk --locked
$env:LIBCLANG_PATH = "C:\Program Files\LLVM\bin"     # нужен LLVM 17.0.6

cd crates/ln8000-kmdf
cargo wdk build --target-arch arm64 --profile release
```

Результат: `target/aarch64-pc-windows-msvc/release/ln8000_kmdf_package/`
(`ln8000_kmdf.sys` 60 КБ, `ln8000_kmdf.inf`, `ln8000_kmdf.cat`, сертификат тестовой
подписи). Контрольная сумма и манифест сборки — `deploy/build-arm64.ps1`,
результат в `artifacts/SHA256SUMS.txt` и `artifacts/BUILD-MANIFEST.json`.
Проверка разрядности:

```powershell
$sys = "target/aarch64-pc-windows-msvc/release/ln8000_kmdf.sys"
$b = [IO.File]::ReadAllBytes($sys); $pe = [BitConverter]::ToInt32($b, 0x3C)
"Machine = 0x{0:X4}" -f [BitConverter]::ToUInt16($b, $pe + 4)   # 0xAA64 = ARM64
```

## 3. Установка на планшете

1. Скопируйте содержимое `artifacts/driver-ln8000-arm64/` в отдельную папку на
   планшете (например `C:\nabu-ln8000\`).
2. Включите тестовую подпись драйверов и перезагрузитесь:

   ```powershell
   bcdedit /set testsigning on
   ```

3. Установите драйвер **от администратора**:

   ```powershell
   cd C:\nabu-ln8000
   .\install-driver.ps1
   ```

   Скрипт проверит режим подписи, поставит пакет, убедится, что устройство
   `ACPI\QCOM057E` получило службу `ln8000_kmdf`, запустит её и напечатает
   состояние.

4. Проверьте режим:

   ```powershell
   .\nabu-ln8000.ps1 status
   ```

Ожидаемое: `режим: SWITCHING 2:1` (если чип подтвердил режим) либо
`BYPASS 1:1` (безопасный запасной вариант), `критичный отказ: нет`.

## 4. Диагностическая утилита

| Команда | Что делает |
|---|---|
| `nabu-ln8000.ps1 status` | режим, состояние сессии, `SYS_STS`, отказы, телеметрия, счётчики |
| `nabu-ln8000.ps1 sessions` | сеансы заряда: текущий и последний (длительность, пиковый ток, пиковая температура, был ли ускоренный режим) |
| `nabu-ln8000.ps1 read 1E` | прочитать регистр LN8000 напрямую (hex) |
| `nabu-ln8000.ps1 write 1E 00` | записать регистр (диагностика) |
| `nabu-ln8000.ps1 journal out.jsonl` | выгрузить снимок состояния в JSON Lines |

Коды управления вычисляются в скрипте по той же формуле, что в
`crates/ln8000-kmdf/src/ioctl.rs`:
`CTL_CODE(0x22, function, METHOD_BUFFERED, FILE_ANY_ACCESS)` →
`GET_STATUS=0x222040`, `READ_REG=0x222044`, `WRITE_REG=0x222048`,
`SET_LIMITS=0x22204C`, `SET_MODE=0x222050`, `GET_SESSIONS=0x222054`,
`GET_SAMPLES=0x222058`.

Все семь кодов реализованы в драйвере:

| Код | Вход | Выход |
|---|---|---|
| `GET_STATUS` | — | режим, отказы, телеметрия, счётчики, код последней ошибки |
| `READ_REG` | `addr` | эхо `addr` + `value` прочитанного регистра |
| `WRITE_REG` | `addr`, `value` | эхо + код ошибки, если запись не прошла |
| `SET_LIMITS` | `iin_ua`, `vbat_uv` (0 — не менять) | `applied_iin_ua` — **фактически** применённый ток (кодирование округляет до шага 50 мА), лимит попадает и в тепловую защиту |
| `SET_MODE` | `mode`: 1 standby, 2 bypass, 3 switching | `applied_mode` — режим, который подтвердил чип |
| `GET_SESSIONS` | — | текущий и последний сеанс с пиками |
| `GET_SAMPLES` | `count` (0 — сколько влезет) | отсчёты подряд после заголовка, `available` — сколько записано |

> **Осторожно: `WRITE_REG` пишет в чип напрямую, мимо всех ворот драйвера.**
> Путь оставлен для разбора инцидентов (когда заряд уже остановлен), но он не
> проверяет ни режим, ни Vin: `nabu-ln8000.ps1 write 1E 01` кладёт в `SYS_CTRL`
> бит 0 `EN_1TO1` и включает обход 1:1 **мимо ворот по Vin** — на 9–12 В входное
> напряжение оказывается на батарее. Внутренний `Pump::enable_bypass` так не
> делает: он отказывается поднимать 1:1 на повышенном Vin
> (`ERR_BYPASS_VIN_OUT_OF_WINDOW = -20` у `SET_MODE 2`). После ручной записи
> сразу верните чип в безопасное состояние — `SET_MODE 1` (standby) или
> `write 1E 00`.

## 5. Обновление и откат

**Обновление** (ставится поверх, старый пакет сохраняется в
`%ProgramData%\nabu-fastcharge\backup`):

```powershell
.\update-driver.ps1
```

**Откат:**

```powershell
.\uninstall-driver.ps1              # останавливает службу и удаляет пакет
# при необходимости — вернуть сохранённую версию:
pnputil /add-driver $env:ProgramData\nabu-fastcharge\backup\ln8000_kmdf.inf /install
```

Драйвер не пишет в прошивку и не меняет настройки питания, поэтому удаление
возвращает устройство к поведению до установки. Транскрипт удаления
сохраняется в `%ProgramData%\nabu-fastcharge\uninstall.log` — это и есть
доказательство отката.

## 6. Профили конфигурации

Значения по умолчанию задаются INF и переопределяются в реестре узла:

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `IinLimitUa` | 2000000 | лимит входного тока, мкА |
| `VbatFloatUv` | 4470000 | целевое напряжение заряда, мкВ (FFC-цель `qcom,fv-max-uv`; 4,42 В — лимит петли QC3, а не порог заряда) |
| `VacOvpUv` | 13000000 | порог перенапряжения входа, мкВ (`BUS_OVP_FOR_QC`) |
| `NtcAlarmCfg` | 226 | порог аларма NTC, 10 бит |
| `TempReduceDc` | 550 | температура, с которой снижается ток (0.1 °C) |
| `TempBypassDc` | 600 | температура ухода в bypass (0.1 °C) |
| `TempStopDc` | 650 | температура останова заряда (0.1 °C) |
| `IinMaxUa` | 3500000 | ток, выше которого срабатывает защита, мкА |
| `IinTargetUa` | 2000000 | ток, к которому возвращается защита, мкА |
| `IinFloorUa` | 500000 | нижняя граница снижения, мкА |
| `VbatReduceUv` | 4450000 | порог полного заряда, мкВ (не-FFC-цель `qcom,non-fcc-fv-max-uv`; FFC — 4470000) |
| `TelemetryMs` | 250 | период телеметрии, мс (допустимо 100…60000) |
| `BusRetryCount` | 2 | повторов операции при сбое шины (0…8) |
| `WatchdogEnabled` | 0 | включить сторожевой таймер чипа (0/1) |
| `ProtectionProfile` | 1 | `1` — петли `V_FLOAT`/`IIN` насоса включены, `0` — как в Device Tree (петли выключены, напряжение держит только аппаратный `VBAT_OV`). Под Windows батарею ведёт насос, а не SMB5, поэтому умолчание — `1` |

**Параметры читаются драйвером при старте устройства** — менять их можно без пересборки.
Ключ: `<устройство>\Device Parameters\Parameters`, то есть например
`HKLM\SYSTEM\CurrentControlSet\Enum\ACPI\QCOM057E\<экземпляр>\Device Parameters\Parameters`.
После правки перезапустите устройство (отключить/включить в диспетчере или
`pnputil /restart-device`). Неверное значение не портит профиль: драйвер его
отклоняет и оставляет прежнее — какие именно значения были приняты, видно в
отладочном журнале драйвера и в `nabu-ln8000.ps1 status`.

Пороги защиты, которые считает сам драйвер (модуль `ln8000::guard`):

| Порог | Значение | Действие |
|---|---|---|
| `temp_reduce_dc` | 550 (55 °C) | снизить входной ток до уставки полосы — `min(профиль, цель)`; при умолчаниях INF (IinLimitUa 2 000 000 = IinTargetUa 2 000 000) полоса совпадает с профилем, и ступень ничего не режет, поэтому ускоренный режим задаёт профиль в реестре (кодовый профиль QC — 2 800 000, тогда полоса равна цели 2 000 000); ниже 520 (52 °C) ток возвращается к профильному |
| `temp_bypass_dc` | 600 (60 °C) | уйти в bypass 1:1 |
| `temp_stop_dc` | 650 (65 °C) | прекратить заряд (standby) |
| `iin_max_ua` | 3 500 000 | снизить ток до целевого 2 А |
| `vbat_reduce_uv` | 4 470 000 (FFC) | у верха заряда держать уставку полосы `min(профиль, цель)`; ниже порога на 50 мВ (4,42 В для FFC) ток явно возвращается к профильному. 4,42 В — лимит петли QC3, по нему ток не режется |

Пороги защиты применяются с проверкой согласованности: если набор получается
бессмысленным (снижение тока позже bypass, цель выше максимума и т.п.), значение
отклоняется целиком и остаются прежние пороги — частично обновлённого набора не
бывает. Отклонённые значения видны в отладочном журнале драйвера.

Строгий профиль `GuardLimits::conservative()` (без ускоренного режима) —
400/430/500 и ток до 1.5 А: применяется, если планшет используется в тепле.

## 7. Типовые сбои

| Симптом | Причина | Что делать |
|---|---|---|
| `не удалось открыть \\.\nabu_ln8000` | драйвер не установлен или устройство не поднято | `install-driver.ps1`, проверить `Get-PnpDevice` по `ACPI\QCOM057E` |
| Драйвер не загрузился, код 52 в диспетчере | тестовая подпись выключена | `bcdedit /set testsigning on` + перезагрузка |
| `режим 2:1 не включился; остаёмся в bypass` | чип не подтвердил `SYS_STS`, либо защита/PD не готовы | смотреть `status`: `FAULT1/FAULT2/SAFETY_STS`; проверить блок питания и кабель |
| `узел PEIC недоступен через Resource Hub` | в `_CRS` нет I²C-подключения (устройство без узла PEIC) | сверить `_HID` в реестре: `HKLM\SYSTEM\CurrentControlSet\Enum\ACPI\QCOM057E` |
| `LN8000 не опознан: неожиданный идентификатор` | прочитан не 0x42 (не тот чип или шина не отвечает) | `nabu-ln8000.ps1 read 00` → ожидается `0x42` |
| Температура растёт, режим падает | сработала защита | это нормально; событие видно в журнале (`actions`), при повторении — строгий профиль |
| Заряд не ускоряется, режим `BYPASS` | согласование 9 В делает Type-C/PD-часть платформы, а не pump | см. раздел 9 «Границы» |

## 8. Реестр рисков

| Риск | Влияние | Оценка | Что делаем |
|---|---|---|---|
| Перегрев кристалла при ускоренном режиме | повреждение узла зарядки | среднее | трехуровневая защита (снижение тока → bypass → stop), журнал событий |
| Ложные значения АЦП (шум, неверный канал) | неверное решение защиты | низкое | решения принимаются по трём каналам, а не по одному; пороги имеют запас |
| Отсутствие ответа шины I²C | зарядка в неизвестном режиме | среднее | таймаут 1 с, до двух повторов, при отказе — устройство в bypass/standby, событие в журнал |
| Обрыв согласования при смене блока | скачок тока | низкое | драйвер не участвует в PD-согласовании; при пропаже питания сеанс закрывается |
| Ошибка в адресах регистров | отказ чипа | среднее | адреса сверены с GPL-драйвером Android, каждая запись проверяется чтением |
| Неверная конфигурация порогов | ускоренный режим не включается | низкое | профили заданы константами из источников, диагностика показывает фактические значения |

**Пошаговый откат:** `uninstall-driver.ps1` → перезагрузка → проверка
`Get-PnpDevice` и `nabu-ln8000.ps1 status` (после удаления утилита не должна
открывать устройство) → при необходимости восстановить прежнюю версию из
`%ProgramData%\nabu-fastcharge\backup`.

## 9. Границы: что драйвер не делает

* **Согласование 9/11 В** выполняет Type-C/PD-часть платформы (PM8150B), а не
  charge pump. Без него LN8000 работает в bypass 1:1 от 5 В либо удерживает уже
  согласованное напряжение. Полные 22.5–33 Вт требуют отдельной работы по PD.
* **Штатный стек зарядки не заменяется**: драйвер управляет только charge pump,
  не дублируя `qcbattmngr8150` (по дорожной карте это риск гонок).
* **Управление зарядом батареи** (профиль, JEITA) — за существующим battery-стеком.

## 10. Протокол приёмочных испытаний

Прогон автоматизирован: **одна команда** проводит по пунктам, снимает телеметрию
драйвера, собирает показания измерителя и формирует итоговый протокол.

```powershell
cd C:\nabu-ln8000
.\run-acceptance.ps1                      # диалог: скрипт спросит показания мультиметра
.\run-acceptance.ps1 -MeterJson .\meter.json   # без диалога, показания из файла
.\run-acceptance.ps1 -DryRun              # проверка конвейера без железа
```

На выходе в `%ProgramData%\nabu-fastcharge\acceptance\`:
`acceptance-<время>.html` (протокол), `.md` (разметка), `.json`
(машинночитаемая сводка) и `journal-<время>.jsonl` (приложенный журнал сеансов).
В отчёт считаются базовый и ускоренный режимы, прирост мощности в процентах,
температура кристалла и режим драйвера в моменты замеров.

Формат `meter.json`:

```json
{ "base_volt": 5.05, "base_amp": 1.80,
  "fast_volt": 9.02, "fast_amp": 2.95,
  "hold_volt": 9.01, "hold_amp": 2.90, "hold_minutes": 10 }
```

Порядок и критерии, которые проверяет скрипт:

| № | Сценарий | Как измеряем | Критерий приёмки |
|---|---|---|---|
| 1 | Базовый режим, 5 В | внешний USB-мультиметр | фиксируем ток/напряжение, мощность как базу |
| 2 | Ускоренный режим | мультиметр + `nabu-ln8000.ps1 status` | режим `SWITCHING`, рост мощности относительно строки 1 |
| 3 | Удержание режима | 10 минут подряд | режим не откатывается к standby, температура ниже `temp_reduce_dc` |
| 4 | Тепловая защита | нагрев (или строгий профиль) | событие в журнале, ток снижен/bypass, заряд не оборван аварийно |
| 5 | Смена блока на несовместимый | переключение блоков | сеанс закрывается, новый сеанс открывается, зависаний нет |
| 6 | Обрыв кабеля при согласовании | вынуть/вставить кабель | устройство возвращается в рабочее состояние, событие в журнале |
| 7 | Перезагрузка | `Restart-Computer` | после загрузки драйвер поднимается, режим восстанавливается |
| 8 | Чистая установка | на устройстве без драйвера | `install-driver.ps1` без ошибок, режим доступен без правок реестра |
| 9 | Откат | `uninstall-driver.ps1` | устройство возвращается к штатному поведению, остаточных служб нет |
| 10 | Повторная установка | `install-driver.ps1` | проходит успешно, счётчики сеансов начинаются заново |

Результаты по каждому пункту: измеренное значение + вывод `nabu-ln8000.ps1
journal` в файл. Итог сводится в `docs/ACCEPTANCE.md`.

### Что уже проверено без железа

Прогон на моке I²C (в ядре LN8000) подтверждает всю логику, кроме физического
подключения: probe `DEVICE_ID = 0x42`, настройка порогов, включение режима 2:1
и его проверка, разбор отказов, чтение АЦП, срабатывание защиты. См.
`artifacts/verify-pump.txt` и 43 теста `cargo test -p ln8000`.

Конвейер отчёта проверен сухим прогоном (`-DryRun`): он формирует HTML,
Markdown и JSON, считает прирост мощности и помечает файл как непроверочный.
Пример — `artifacts/acceptance-dryrun/`.
