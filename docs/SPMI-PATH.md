# Доступ к регистрам PMIC: что подтвердил реверс

Вопрос, который висел дольше всего: каким протоколом штатные драйверы Qualcomm
читают регистры PMIC, и как повторить это из нашего драйвера. Ниже — метод,
находки с адресами и вывод. Всё проверяемо: скрипты и выгрузки лежат рядом.

## Метод

1. **Заголовки WDK.** Проверено `shared/reshub.h` (WDK 10.0.26100): там есть
   только макросы путей (`RESOURCE_HUB_DEVICE_NAME`,
   `RESOURCE_HUB_CREATE_PATH_FROM_ID`) и структуры параметров подключений
   (`RH_I2C_CONNECTION_PARAMETERS` и прочие). Структур транзакции и кода
   `IOCTL_RESOURCE_HUB_TRANSACT` в публичных заголовках **нет**.
2. **Реверс бинарников** (Ghidra 12.1.3 headless, проект `nabu`):
   * `FindTransact.java` — поиск констант `0x32C004`, `0xC004`, `0x8B012`
     в операндах и декомпиляция найденных функций;
   * `DecompAt.java` — точечная декомпиляция по адресам.

## Находка 1: серверная сторона (`qcspmi8150.sys`)

Функция `FUN_140003270` (единственное попадание на `0x32C004` в сервере хаба)
сама **посылает** этот код нижнему устройству шины:

```c
iVar2 = (*pcVar11)(DAT_14000a368, uVar6, 0, 0x32c004, &uStack_d0, &local_e8, 0, auStack_b8);
```

Далее она проверяет полученный буфер:

```c
if ((((int)local_b0 != 0x426f6541) || ((int)local_a8 == 0) ||
    ((local_a8._4_2_ != 2) || (local_a8._6_2_ < 0x1a)))) { ... }
```

и для ресурса типа 3 (подключение) отображает регистры контроллера в память:

```c
uVar6 = MmMapIoSpaceEx(*(undefined8 *)(pcVar8 + 4), iVar4, 0x204);
```

То есть `0x32C004` — это **шаг подключения** (получить и отобразить контроллер), а
не доступ к отдельному регистру.

## Находка 2: клиентская сторона (`qcpmicEIC8150.sys`)

Функция `FUN_1400026f0` (клиент) готовит запрос подключения:

```c
piVar7 = ExAllocatePoolWithTag(0x200, 0x400, 0x31337071);   // 1024 байта
memcpy_s((void *)((longlong)&local_98 + 4), 4, &DAT_140007178, 4);
local_98 = CONCAT44(local_98._4_4_, 0x42696541);            // младшие 4 байта — сигнатура
local_60 = &local_98;  local_58 = 8;                        // вход: 8 байт
local_70 = 0x400;                                           // выход: 1024 байта
iVar3 = (*pcVar11)(DAT_140008608, uVar13, 0, 0x32c004, &local_68, &local_80, 0, &local_88);
```

Полученные 1024 байта разбираются в контекст устройства (`FUN_140001618`), после
чего **ставится таблица функций доступа к регистрам**, причём разная для версий
контроллера (`piVar6[0x32] == 1` или `2`) — в выгрузке видно два набора по 18
указателей.

## Находка 3: доступ к регистрам — публичный интерфейс SPB

Примитивы доступа — `FUN_140003a40` (запись) и `FUN_140003778` (чтение). Внутри
`FUN_140003a40`:

```c
iVar2 = (*pcVar4)(DAT_140008608, uVar1, local_128, 0x41808, &local_118, 0,
                  &local_a8, auStack_120);
```

`0x41808` — это

```text
CTL_CODE(FILE_DEVICE_CONTROLLER = 0x04, 0x602, METHOD_BUFFERED = 0, FILE_ANY_ACCESS = 0)
= 0x04 << 16 | 0x602 << 2
= 0x0004_1808 = IOCTL_SPB_EXECUTE_SEQUENCE
```

**Вывод: приватного протокола доступа к регистрам нет.** Регистры PMIC читаются
и пишутся обычным списком передач SPB (`SPB_TRANSFER_LIST`) — тем же публичным
интерфейсом, который использует наш драйвер LN8000 на шине I²C. Именно поэтому
поиск «раскладки ответа с значением регистра» ничего не давал: такого ответа не
существует.

Для наглядности: функция `FUN_140004590` (инициализация версии 1) пишет `0x40`
в регистр `0x30`, читает регистр `0x32`, сбрасывает в нём бит 2 и пишет обратно —
типовая последовательность инициализации контроллера.

## Что это меняет в нашем коде

| Было | Стало |
|---|---|
| SMB-драйвер посылал хабу догадку: байт «признак операции», два байта адреса, значение | Драйвер собирает настоящий `SPB_TRANSFER_LIST` и посылает `IOCTL_SPB_EXECUTE_SEQUENCE` |
| ABI SPB был скопирован внутри драйвера LN8000 и нигде не проверялся | Общий крейт `crates/spb`: ABI, сборка последовательностей и путь Resource Hub покрыты тестами на хосте |
| Чтение регистра возвращало отказ «раскладка не подтверждена» | Чтение реализовано последовательностью «адрес (16 бит), затем байт» |

Параметр `SpmiConfig::address_big_endian` задаёт порядок байт адреса (по умолчанию
старший байт первым — по спецификации SPMI) и **требует подтверждения на
железе**: это единственное допущение, которое осталось в транспорте, и оно
вынесено в конфигурацию, а не зашито в код.

## Что ещё не сделано и почему

* **Шаг подключения (`0x32C004`) не выполняется.** Штатный клиент получает через
  него цель ввода-вывода шины SPMI. Наш драйвер открывает устройство хаба по
  имени и посылает последовательность ему; на железе это может не сработать, и
  тогда запрос честно вернёт ошибку транспорта.
* **Правильное решение — взять подключение SPMI из `_CRS` своего узла** (путь
  строится функцией `spb::resource_hub_path`). Для этого драйверу нужен колбэк
  подготовки ресурсов (`EvtDevicePrepareHardware`), которого у него сейчас нет:
  транспорт открывается прямо в `EvtDeviceAdd`. Это отдельная работа, и она
  требует проверки на устройстве, потому что зависит от того, какой узел ACPI
  достанется драйверу.

## Побочный результат: тесты поймали ошибку раскладки

Общий крейт писал первую передачу за заголовком списка, тогда как по `spb.h` она
лежит **внутри** заголовка (`Transfers[1]`), и `sizeof(SPB_TRANSFER_LIST)`
уже включает её. Тест `area_size_counts_first_entry_in_header` это выявил.

В собранном драйвере LN8000 раскладка была верной (первая передача берётся как
`transfers[0]`, последующие — от `header_size()`), поэтому правка потребовалась
только новому крейту: `area_size` теперь считает
`sizeof(list) + (count − 1) · sizeof(entry)`.
